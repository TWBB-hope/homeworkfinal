## 一、需求理解与任务管理

### 1.1 需求分析

**解决什么问题。** 学校把运动场馆的开放信息放在一篇学期初发布的推送里，把预约入口放在另一个系统里，把"现在还有没有空位"这件事留给人到现场看。结果是：想打球的人要来回翻三个地方，仍然不知道"此刻北区羽毛球馆还有没有名额"。本作品把这三类信息合并到一处：**查得到开放情况、看得懂拥挤程度、约得上具体时段**。

**服务什么人。** 主要是三类人，需求各不相同：

| 使用者 | 他要解决的问题 | 作品里对应什么 |
| --- | --- | --- |
| 想去锻炼的学生 | 现在哪个场馆还进得去、要不要钱、离我近不近 | 首页"今日开放速览"（按整点看剩余名额）、场馆页筛选与排序 |
| 已经约了场的学生 | 我约了哪几场、临时有事要换时段 | "我的预约"增·改·删，保存在本机浏览器 |
| 场馆负责的学生干部／教师 | 一周里哪天人次最多、哪类场地最紧张、哪个校区被用得最少 | 数据分析页三类图表 ＋ 统计口径与一致性自检 |

**包含哪些功能模块。** 六个模块，全部为必须项：

1. 信息首页：概览四卡、按整点时段的开放速览、公告、功能入口。
2. 场馆查询：类型／校区／拥挤程度／预约方式／排序／多关键字／指定时段剩余名额下限，共 7 项条件，表格与卡片双视图。
3. 预约管理：添加、修改、取消，含冲突与上限与名额校验，本机持久化。
4. 数据加载：本地 `data/facilities.json` 六张表，四个页面共用一个取数模块。
5. 数据可视化：折线、环形、水平条形三类图表，随口径联动，附一致性自检。
6. 三维展示：Three.js 按校区分组的场馆场景，与主数据同源。

另有贯穿性的错误提示、响应式适配与可访问性处理。

## 二、页面结构、样式与可用性

### 2.1 页面结构说明

**页面清单（1 个首页 ＋ 3 个功能页面，超过"至少 2 个功能页面"的要求）**

| 页面 | 文件 | 语义化主干 | 主要数据来源 |
| --- | --- | --- | --- |
| 信息首页 | `index.html` | `header>nav`、`main` 内 5 个 `section`（概览／速览／公告／入口／关于）、`footer` | `facilities`＋`slotBookings`＋`notices` |
| 场馆查询与预约 | `facilities.html` | `section`（查询条件含 `form`＋`table`／卡片组、我的预约含 `ul`） | `facilities`＋`slots`＋`slotBookings` |
| 使用数据分析 | `statistics.html` | `section`（口径表单、三张图表卡、自检卡、来源说明） | `facilities`＋`slotBookings`＋`history` |
| 校园三维导览 | `venue-3d.html` | `section`（操作面板、`role="application"` 场景、定位清单、主题说明） | `areas`＋`facilities`＋`slotBookings` |

**结构说明（以 `facilities.html` 为例，其余三页同一套写法）**

| 页面区块（语义化元素） | 该区块放置的内容 |
| --- | --- |
| `<a class="skip-link">` | 键盘用户"跳到主要内容"的隐藏链接，获得焦点时可见 |
| `<header><nav aria-label="主导航">` | 品牌名、四个页面入口（当前页 `active`＋`aria-current`）、数据状态文字 |
| `<main>` → `<h1>`＋说明段 | 页面标题"场馆查询与预约"与一句话用法提示 |
| `<section aria-labelledby="queryTitle">` → `<form id="queryForm">` | 七项查询条件（类型／校区／拥挤度／预约方式／排序／关键字／剩余名额下限）＋清空按钮＋条件回显 |
| 同 section 内 `<role="group">` 单选组 | 表格视图／卡片视图切换 |
| `<table class="data-table">` | 场馆明细：名称、类型、校区、容量、开放时间、费率、今日人次、峰值占用、操作；`<caption>` 写口径与单位 |
| `<section>` 内 `<ul id="myBookingList">` | 我的预约列表，每条带"修改时段""取消"按钮 |
| `<footer class="site-footer">` | 课程与选题信息、数据为虚构声明、作者与年份 |

**导航关系。** 顶部导航四页互达，当前页用 `active` 加 `aria-current="page"` 标出；页脚在四页统一。除主导航外有三条**跨页数据链**：

```
index.html ──"三维定位"──▶ venue-3d.html?id=4 ──HUD"在查询与预约页打开"──▶ facilities.html#f4
    │                                                                       │
    └──"去预约"──▶ facilities.html#f4 ◀──表格/卡片"在三维场景查看"───────────┘
statistics.html ◀── 与上面三页共用同一份派生结果（同一时段人次数字四处一致）
```

`#f<id>` 与 `?id=<id>` 两种链接都做了对端处理：目标行／建筑会被高亮并滚动到位，hash 处理完立即清理，避免刷新后重复弹提示；编号在数据里找不到时给出黄色提示而不是静默失败。

**语义化与结构约定。** 每页只有一个 `h1`（页面标题），区块标题用 `h2`／`h3` 逐级递进；每个 `section` 用 `aria-labelledby` 指向自己的标题；表格有 `caption`（口径说明）与 `th scope`；公告日期用 `time datetime`；三维容器 `role="application"` 并在 `aria-label` 里说明可做的操作。页面顶部另有"跳到主要内容"的 `.skip-link`。

### 2.3 可用性说明

**界面一致性。** 四页共用同一套骨架（同一导航、同一页脚、同一提示条容器 `#messages`）与同一套设计变量（主题色、强调色、卡片描边在 `css/base.css` 的 `:root` 里集中定义）。同一指标在四页用同一套词："今日人次""峰值占用""宽松／适中／紧张""自由进场""暂停开放"。占用分档阈值（50%、80%）只在 `Campus.loadLevel()` 写一次，表格徽章、首页名额条、三维屋顶灯全部复用它，不会出现"表格里是黄色、三维里是红色"的情况。

**操作提示。** 每个会改变状态的动作都有即时反馈，且提示里包含**下一步做什么**：
- 点"预约此馆"→ 页面滚动到表单、自动带入场馆、时段下拉获得焦点，提示"请在下方预约表单里选择时段后提交"。
- 时段下拉里直接写明"19:00-20:00（剩 1 个名额）"，约满的时段置灰不可选，把错误挡在提交之前。
- 添加成功："已添加预约：…该时段还剩 0 个名额。刷新页面后仍在。"
- 修改模式：按钮文字变"保存修改"并出现"取消修改"，表单上方说明"保存后原时段名额立即释放"。
- 三维页每个控件都有文字说明，另配"点选不便时：从列表直接定位"按钮组，照顾手指点不到小建筑的手机用户。

**错误提示。** 三类原则：说清**是什么**（HTTP 404 与"HTTP 200 但 JSON 解析失败"是两条不同提示）、说清**怎么办**（分别提示 `git restore` 与 `python -m json.tool`）、**不夸大也不隐瞒**（降级时导航栏状态从"数据就绪"改成"降级：备份数据"或"数据为空 · 0 个场馆"，让人一眼看出现在看到的不是真实文件的内容）。提示条可手动关闭，危险级用 `role="alert"`，其余用 `role="status"`，不干扰屏幕阅读器读其他内容。

### 3.2 数据处理说明

**数据组织。** `data/facilities.json` 六张表，`meta` 里写有每个字段的中文说明、单位与三条统计规则：

| 表 | 内容 | 被谁使用 |
| --- | --- | --- |
| `meta` | 单位、更新时间、统计截至、口径规则 | 四页的"数据来源"文字与提示语 |
| `areas` | 5 个校区（名称、颜色、场景坐标） | 三维分组、校区跳转、折线图系列 |
| `facilities` | 14 个场馆主表（容量、开放区间、费率、可否预约、状态） | 全部页面 |
| `slots` | 14 个整点时段 | 时段下拉、可约判断 |
| `slotBookings` | 今日各场馆各时段已约人数（稀疏表，未列出即 0） | 剩余名额、今日人次、峰值占用、折线今日点、条形图 |
| `history` | 近 6 天各校区预约人次 | 折线图历史部分 |
| `notices` | 4 条公告 | 首页公告栏 |

**核心设计：派生而非存储。** 作品里没有 `occupancy` 字段。某场馆某时段的已约人数 ＝ `slotBookings` 的记录 ＋ 本机 `localStorage` 里"我的预约"；今日人次 ＝ 各时段之和；峰值占用 ＝ 最拥挤时段人数 ÷ 容量。这三步只在 `js/data.js` 的 `stats()` 里做一次，四个页面都调用它。折线图的"今日"点同样由 `stats()` 汇总，不在 `history` 里再存一份——这是"改一条预约、四个页面同步变化"能成立的原因（实测见 T27）。

**加载 → 解析 → 展示流程。**

```
页面脚本 C.ready()
  └─ Campus.bindSharedUi()            绑定共用导航与页脚
  └─ CampusData.load(boot)
       └─ Campus.getJson('data/facilities.json', {_: 时间戳})   绕开浏览器缓存
```

### 3.4 关键代码说明

#### 关键代码一：单一取数口径（`js/data.js:237` 起）

```js
/* 今日指标：人次 = 各时段已约之和（可大于容量，人次本就按次计），
   峰值占用 = 最拥挤那一个时段的人数 ÷ 容量（这才是"名额紧不紧张"） */
function stats(facility, mine) {
  var overrides = mine || myBookingMap();
  var bookedToday = 0, peakCount = 0, peakSlot = '';
  availableSlots(facility).forEach(function (slot) {
    var n = slotCount(facility.id, slot, overrides);   // JSON 记录 + 我的预约
    bookedToday += n;
    if (n > peakCount) { peakCount = n; peakSlot = slot; }
  });
  var ratio = facility.capacity ? peakCount / facility.capacity : 0;
  return {
    bookedToday: bookedToday, peakCount: peakCount, peakSlot: peakSlot,
    peakLoad: ratio, level: C.loadLevel(ratio),
    remainingOf: function (slot) {
      return Math.max(0, facility.capacity - slotCount(facility.id, slot, overrides));
    }
  };
}
```

**实现思路。** 这是全项目的"唯一事实来源"。四件事一次做完：
1. `availableSlots()` 先把该场馆可约的整点时段算出来——判据是时段的起止分钟都落在 `openFrom`–`openTo` 内，所以"开放区间"只需要两个字段，不必为每个场馆再存一份时段列表（数据冗余少一处，就可能少一处不一致）。
2. `slotCount()` 把 JSON 里的记录数与本机"我的预约"合并，因此用户加一条预约后，剩余名额、今日人次、图表与三维屋顶灯会一起变。
3. 返回的 `peakLoad` 用**最拥挤时段**而不是全天平均，因为"还剩不剩名额"取决于高峰那一刻；平均占用会让 47/48 的羽毛球馆看起来不紧张。
4. `remainingOf()` 以闭包形式带出，让调用方（时段下拉、卡片、校验）用同一个函数算剩余，避免各处自己写 `capacity - booked`。
`level` 复用 `Campus.loadLevel()` 的阈值，保证表格徽章、首页占用条与三维屋顶灯三色永远一致。

#### 关键代码二：预约的六道校验（`js/facilities.js:293` 起）

```js
function validate(facilityIdText, slot, list, editingId) {
  if (!facilityIdText) return { error: '请先选择要预约的场馆，再选择时段。' };
  if (!slot) return { error: '请先选择时段。若时段下拉框是灰的，说明该场馆今日没有可预约的整点时段。' };
  var facility = D.facilityById(facilityIdText);
  if (!facility) return { error: '编号 ' + facilityIdText + ' 的场馆已不在数据中，请重新选择。' };
  if (!facility.bookable || facility.status !== 'open') {
    return { error: facility.name + ' ' + (facility.status === 'open' ? '为自由进场场馆，无需预约。' : '本学期暂停开放，不能预约。') };
  }
  if (D.availableSlots(facility).indexOf(slot) === -1) {
    return { error: facility.name + ' 在 ' + slot + ' 不开放（开放区间为 ' + facility.openFrom + '–' + facility.openTo + '），请换时段。' };
  }
  var duplicated = list.filter(function (b) {
    return b.id !== editingId && String(b.facilityId) === String(facility.id) && b.slot === slot;
  });
  if (duplicated.length) return { error: '该场馆的 ' + slot + ' 时段你已经约过了，请换一个时段或先取消原记录。' };
  if (D.stats(facility).remainingOf(slot) <= 0) {
    return { error: facility.name + ' 的 ' + slot + ' 名额已满（容量 ' + facility.capacity + ' 人），请换一个时段。' };
  }
  if (!editingId && list.length >= D.MAX_MY_BOOKINGS) {
    return { error: '最多保留 ' + D.MAX_MY_BOOKINGS + ' 条练习预约，请先取消一条再添加。' };
  }
  return { facility: facility };
}
```

**实现思路。** 校验被抽成一个**纯函数**：输入场馆、时段、现有记录、正在修改的记录 id，输出 `{error}` 或 `{facility}`。这样做有三个好处：
1. 添加与修改复用同一段逻辑，只在两处传不同的 `editingId`。修改时把"自己这一条"排除在重复判断之外，否则改到同一时段会自己和自己冲突。
2. 顺序按"代价从小到大"排：先查空值，再查数据是否存在，再查业务规则，最后才做需要遍历全部时段的 `remainingOf()`；失败即返回，不做多余计算。
3. 每条提示都带上**具体数字与下一步**（容量多少、开放区间是多少、该换时段还是先取消），而不是一句"输入非法"。

前端已经把这些挡住，`validate()` 仍是最后一道防线：时段选项里置灰的项、以及另一个标签页改动的记录，都可能绕过界面直接提交，所以这里必须再判一次。校验通过后由 `submitBooking()` 写入 `localStorage`，并**在保存之后**重新调用 `remainingOf()` 生成提示——保存前算会漏掉自己刚提交的这一条，显示成多 1 个名额（开发中真实踩到，见 `docs/dev-log.md` B3）。

### 4.3 选型说明

**为什么选 Chart.js 而不是 ECharts。** ① 课堂讲授用的是 Chart.js 画折线与环形，本项目不引入未学过的配置体系；② 三类图都在"单图几十个数据点"的量级（最多 5 条曲线 × 7 个点、5 个扇区、12 根柱子），Chart.js 完全够用，ECharts 的数据缩放、地图、主题注册等能力在这里用不上；③ Chart.js 的 UMD 单文件 205KB，比 ECharts 的 1MB 小得多，配合 `vendor/` 兜底时下载更快；④ 需要的一点定制（环形图中心写总数）用一个 15 行的行内插件 `centerNumber` 就实现了，不必换库。

**为什么是这三种图表类型。** 选择依据是"要回答的问题的形状"：

| 要回答的问题 | 选了什么 | 为什么不用别的 |
| --- | --- | --- |
| 一周里哪天人次最高、哪个校区用得最多 | 折线图（按校区分系列） | 条形图也能画，但 5 个校区 × 7 天会挤成 35 根柱子；折线能直接看出趋势与周末抬升 |
| 全校场馆按运动类型怎么分布 | 环形图 | 类型只有 5 类且合计就是 14，环形能同时表达"份额"和"总量"（中心数字）；用柱状图会丢掉"占整体多少"的直觉 |
| 今日哪些场馆最抢手、排第几 | 水平条形图 | 场馆名是长中文，竖直条形的 x 轴标签必须斜排或截断；横向条形让名称完整可读，并按值降序直接表达排行 |
| 单个时段还剩多少名额 | HTML＋CSS 进度条（非图表库） | 只有 1 个数值，为它初始化一张 canvas 图不值得，也拖慢首屏 |

另有一条实现层面的选择：**图表只创建一次**，改筛选条件时替换 `data` 后调用 `update()`，不重复 `new Chart()`。重复初始化会造成画布闪烁，也会遗留旧实例（内存与事件都不会释放）。

### 5.2 主题关联说明

**与主题的关系。** 统一题目是"校园公共信息与数据展示中心"，而运动场馆的信息天然有两半：一半是**数字**（容量、费率、占用），一半是**空间**（在哪个校区、离宿舍多远、旁边是不是跑道）。表格只能给前一半。三维场景把两半画在同一栋"楼"上：位置＝校区分组与地面指引线，规模＝建筑高度，用途＝建筑颜色，拥挤度＝屋顶指示灯颜色。

**为什么这个作品需要三维。** 三条具体理由：
1. **校区差异只有摆在平面上才看得见。** 数据里西区只有 2 个场馆且攀岩墙施工中、中心区 4 个场馆且承担了一半人次——这在表格里是两行数字，在场景里是"中心区那堆楼最密最亮、西区只有一栋灰的"，一眼就能形成"该往哪边走"的判断。
2. **拥挤度需要一个不靠颜色的第二通道。** 场景里"哪栋楼顶上亮红灯"配合"哪栋楼最高"，共同表达"大场馆也未必约得上"，这是单张图表表达不了的组合信息。
3. **它是指南要求的"与主题相关的三维展示区"，而不是装饰。** 建筑不是随便放的模型：每一栋对应 `facilities` 里的一条记录，点它能拿到与表格完全相同的今日人次与剩余名额，还能一键跳回预约页。删掉这个页面，作品只是少了"看位置"这一维；删掉那些编码关系，这个页面就没有存在价值——所以它承载的是信息，不是特效。

**三条视觉通道互不混用**（这是场景可读的关键）：

| 通道 | 表示 | 取值来源 |
| --- | --- | --- |
| 建筑高度 | 容量（人） | `facilities.capacity`，`4 + min(26, capacity/8)` |
| 建筑颜色 | 运动类型 | `facilities.type` → 五色表 |
| 屋顶灯颜色 | 峰值占用分档 | `stats().level`，与表格徽章同一套阈值 |
| 半透明＋围挡 | 暂停开放 | `facilities.status` |

## 七、个人反思与现场解释

### 7.1 个人反思

**最大亮点：把"数字对得上"从一句承诺变成了页面上看得见的结论。**
作品里没有第二个数据源——占用率、今日人次、剩余名额全部由 `CampusData.stats()` 现算，折线图的"今日"点也是从时段记录表汇总出来的。因此分析页可以放一张"数据一致性自检"卡，用两条互相独立的算法（逐场馆求和 vs 逐时段累加 vs 折线今日点合计）把同一个数字算三遍并展示结论；本机新增一条预约后，首页卡片、场馆表格、条形图、折线今日点、三维屋顶灯会同时变化，而自检依然通过。这个设计是在开发中被逼出来的：一开始我在 JSON 里直接存 `occupancy`，加了"我的预约"之后表格与图表就开始打架，才改成全部派生。它带来的实际收益是——我敢在报告里写"任何一处数字不一致都会自己暴露"。

**最大不足：数据是静态快照，"管理"只到浏览器这一层。**
预约写在 `localStorage`，换一台电脑或清缓存就没了；`slotBookings` 也不会因为别人预约而增长，所以"名额"只是我这一台机器上的自洽，不是全校的真相。这让"管理模块"实际上退化成了"个人练习工具"。次要不足还有两个：场馆的开放区间是整点粒度，处理不了"18:30 清场"这类真实规则；三维场景没有高度方向上的遮挡处理，密集校区里后排建筑会被前排挡住，只能靠旋转或列表按钮补偿。

### 7.2 局限性与改进

**当前局限（如实列出）。**

| 局限 | 具体表现 |
| --- | --- |
| 无后端，预约不共享 | 换浏览器／设备即丢失；无法体现"被别人约走"的名额变化 |
| 数据静态 | 统计截至 2026-09-19 14:00，深夜打开会看到"当前时段无场馆开放" |
| 时段粒度粗 | 只有 14 个整点时段，不支持半点、连续两时段连订、按人数订场 |
| 无身份与权限 | 没有登录，无法区分学生与场馆管理员，"审核／改期"这类流程做不了 |
| 三维遮挡与精度 | 密集校区后排建筑被挡；点选要求位移 <6px，手指抖动可能选不中（已用列表按钮兜底） |
| 无障碍未做机器验证 | 语义标签、`aria-*`、键盘可达都写了，但没用屏幕阅读器实测过 |
| 单页体积 | 三维页要下载 Three.js（约 600KB），首屏在弱网下偏慢（已用 `vendor/` 兜底） |

**再有一周时间的改进计划（按性价比排序）。**

| 天 | 做什么 | 为什么先做它 |
| --- | --- | --- |
| 第 1 天 | 把 `slotBookings` 的读写抽成 `DataProvider` 接口，保留本地 JSON 实现，另写一个 `fetch` 实现指向教师统一提供的数据地址 | 这是后面所有"共享"能力的前提，且能立刻验证抽象是否干净 |
| 第 2 天 | 预约冲突改为服务端语义：提交后拉一次该时段最新记录，若已被占则回滚并提示"刚刚被别人约走" | 让"名额"第一次变成真共享，直接补掉最大不足 |
| 第 3 天 | 时段粒度改为可配置（整点／半点），支持连订两小时；校验里加"同一时段不能约两个不同场馆" | 真实规则比现在的整点表复杂，这是功能层面最有价值的补强 |

### 7.3 现场解释确认

本人确认已熟悉本作品的全部代码，包括每个页面的结构、样式分层、`common.js` 工具、`data.js` 的取数与派生、四个页面脚本的逻辑与所有降级分支。开发过程中的 8 个缺陷及其成因与修复方式逐条记录在 `docs/dev-log.md` 第二节，可现场复述来龙去脉。

**最希望现场展示的部分（按顺序）：**

1. **`js/data.js` 的 `stats()` 与 `weekSeries()`（报告 3.4 关键代码一）** —— 请老师随机改一个场馆的容量或某个时段的人数，我当场演示首页卡片、场馆表格、三张图表、三维屋顶灯如何同步变化，以及为什么它们不可能对不上。
2. **`js/facilities.js` 的 `validate()`（报告 3.4 关键代码二）** —— 六道校验的顺序与提示语设计，以及为什么修改模式要传 `editingId`。
3. **分析页的"数据一致性自检"卡** —— 现场把某个时段的人数改到超过容量，看自检从"通过"变"不通过"并在顶部弹红色提示，说明我没有靠"看起来一致"来交差。
4. **`js/venue3d.js` 的射线拾取与相机插值** —— 点选、旋转、`?id=` 定位，以及 `visibilitychange` 停渲染循环的原因。

## 附一、收获和问题解决

### 1、知识总结

`$.getJSON` 是 `$.ajax` 的语法糖，但它**默认允许浏览器缓存**：同一 URL 第二次请求可能直接命中缓存回到 `done` 回调，看到的还是旧文件——这就是"改了 JSON 页面不动"的真相。要绕开它，给请求带一个每次都变的查询参数（`$.getJSON(url, {_: Date.now()})`）即可，不必换成 `fetch` 再自己写 no-store。jQuery 的 `on('change', 'select', fn)` 是事件委托，第二个参数传选择器，所以后来动态插入的表格行、预约条目一样能被捕获；回调里的 `this` 是原生 DOM 元素，要用 `$(this)` 包一层才能继续用 jQuery 方法，`.data('id')` 读的是 `data-id` 属性并且已经自动转成数字，比较时要留意类型。

Chart.js 的 `type` 写在配置顶层，多条序列放在同一个 `datasets` 数组里；容器必须有确定高度（我给 `.chart-box` 写死 320px，手机端改 260px），否则 canvas 高度算出来是 0，图就"不见了"。改数据时把新值赋给 `chart.data` 再 `chart.update()`，**不要重新 `new Chart()`**——重复初始化会遗留旧实例（事件与内存都不释放），还会闪。要彻底换掉配置才用 `chart.destroy()`。环形图中心写总数这类定制，Chart.js 没有内置，注册一个只含 `afterDraw` 的行内插件即可，插件通过配置里的 `plugins: [插件对象]` 只挂到某一张图上，不必污染全局。

Three.js 的最小闭环是"场景＋相机＋渲染器＋渲染循环"四件。本项目没有用 OrbitControls（那是 examples 里的额外文件），而是自己用球坐标写轨道相机：记 `radius/theta/phi` 三个量，每帧换算成 `camera.position` 再 `lookAt(target)`；目标点用 `Vector3.lerp(desired, 0.12)` 逐帧插值，跳转就是平滑移动而不是瞬移。点选用 `Raycaster`：先把鼠标坐标换算成设备坐标（x、y 都在 −1～1 之间，注意 rect 尺寸为 0 时直接返回，否则除零），再 `setFromCamera` 与 `intersectObjects`；求交前要把隐藏的物体过滤掉，不然会拾取到看不见的建筑。拖拽与点击的区分靠累计位移（<6px 才算点击）。`CanvasTexture` 可以把 canvas 上画的中文变成 `Sprite` 贴图，`Sprite` 天然面向相机，适合做校区名称标签。最后两条教训：`MeshLambertMaterial` 要看到明暗必须有光源，只设 `color` 不add灯会是一片死黑；`requestAnimationFrame` 不会因标签页不可见而自动停，必须自己监听 `visibilitychange` 停／启，否则后台空转、切回主页面时明显卡顿。

数据层面最大的收获是**"派生优于存储"这件事在纯前端项目里同样成立**。原型里我在 JSON 存了 `occupancy`，加了本机预约之后表格与图表就开始打架；改成只存"每个时段约了几个人"，占用率、今日人次、剩余名额全部由一个函数现算之后，四个页面不可能再给出两个版本的事实，一致性也从"我保证"变成了页面上能看见的自检结论。另外三条：`localStorage` 在隐私模式下会抛异常，任何一次读写都可能失败，必须包 `try/catch` 并且失败后仍让页面可用；`toISOString()` 给的是 UTC 时间，直接显示会比本机时间早 8 小时；往 `innerHTML` 里拼任何来自用户输入或存储的文本之前必须转义，否则轻则结构错乱、重则脚本注入。语义化标签不只是习惯问题：`section` 配 `aria-labelledby`、图表配 `role="img"`＋`aria-label`、颜色之外再给文字与数字，屏幕阅读器和色觉障碍用户才读得懂同一张页面。

### 2、问题解决

**问题一：改了 `data/facilities.json` 里的数字，刷新页面四个页面却一个都没变，一度以为自己的降级代码写错了。**

排查与解决：先看 Console 没有报错，再看 Network 面板，发现 `facilities.json` 那一条请求返回的是 `(from disk cache)`，根本没有回到服务器。原因是 `$.getJSON` 默认允许缓存，而 Python 的简易服务器不带 `Cache-Control` 头，浏览器就按启发式规则直接复用了上次的响应。解决办法是给请求加一个每次都变的查询参数（新增 `C.getJson()`，内部 `$.getJSON(url, {_: Date.now()})`），这样 README 里"改完 JSON 刷新即见"的说明才真正成立。这个坑的收获是：**判断"代码没生效"之前，先看请求有没有真的发出去**。

**问题二：分析页先把筛选条件调到 0 条结果、再放宽回来，控制台抛 `Cannot read properties of null (reading 'id')`，三张图全部消失。**

排查与解决：报错来自 Chart.js 构造函数，说明它拿到的 canvas 是 `null`。回头看自己的空数据分支——为了给出"没有可统计的场馆"的提示，我用 `.html()` 把 `.chart-box` 的内容整体换成了提示文案，canvas 因此被删掉了；而重建图表时我写的是 `$('#weekChart').closest('.chart-box')`，元素已经不存在，`closest()` 返回空集合，于是什么都没恢复。修复是把三个容器写成有 id 的 `#weekBox／#typeBox／#rankBox`，恢复时按容器 id 重建 canvas 再建图；顺带把"主表为空"和"筛选后为 0"两种情况的文案分开，不再用同一句话糊弄两种事实。

**问题三：添加预约后提示"该时段还剩 1 个名额"，可时段下拉里同一档明明显示"剩 0 个名额"，两处自相矛盾。**

排查与解决：在 `submitBooking()` 里下断点单步，发现提示用的剩余名额是在写入 `localStorage` **之前**算的，那一刻我自己的这一条还没进统计，于是永远多 1 个。改成保存成功之后重新调用 `D.stats(facility).remainingOf(slot)` 再拼提示语，两处数字立刻一致。这个 bug 的根因不是算术错，而是**同一个量在两个时间点各算了一遍**——和报告第三部分强调的"只有一处派生函数"是同一个道理，只不过这次错的是时间点。

**问题四：预约列表里"提交于"显示的是凌晨 02:00，而当时本机是上午 10:00。**

排查与解决：02:00 与 10:00 差 8 小时，正好是 UTC+8 的偏移，说明我取的是 UTC 时间——代码里用了 `new Date().toISOString().slice(0,16)`，`toISOString()` 永远返回 UTC。改成本机时间逐段拼接（年、月、日、时、分各自补零）。顺带在首页"当前时间"处也统一用同一个本地时间函数，避免两处时钟不一致。

**问题五：三维页在 Three.js 加载失败时，整个页面停在"建筑含义加载中…"，看起来像程序挂死。**

排查与解决：`boot()` 在检测到库缺失时直接 `return`，后面的图例、编码说明和场馆清单都没来得及渲染。补一个 `renderTextFallback()`：库缺失时把三维舞台收起来，仍然画出图例、说明文字和一份带峰值占用的文字版场馆清单（每项都能跳回查询页）。降级不等于白屏——**报错提示要说清"什么坏了"，更要给出"那我现在能干什么"**。
